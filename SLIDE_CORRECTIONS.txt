SLIDE CORRECTIONS for LSB_Steganography.pptx
=============================================

The original deck is NOT edited by this project. This file lists, slide by slide, what no
longer matches the finished project, with the exact current wording (read with markitdown
0.1.9 on 2026-10-22) and a suggested replacement. The team edits the slides by hand.

Main differences between the deck and the finished project:
  * Delimiter        -> 13-byte header (signature "LSBS", version, length, CRC32); no delimiter.
  * Image only       -> image AND video (video = the same method applied frame by frame).
  * "Secure"         -> covert communication: hidden, NOT encrypted, NOT secure.
  * Unmeasured claims ("visually identical", "no perceptible distortion") -> what we measured
    (no visible difference in our side-by-side figures; PSNR values measured on our covers).
    We did not run any test with human viewers.

               LSB-based Image Steganography System"
    Replace:  "Design and Implementation of an
               LSB-based Image and Video Steganography System"
    Why:      the project also hides text in video (lossless FFV1 MKV output).

    Replace:  "A project on covert communication using digital images and video"
    Why:      there is no encryption; the message is only hidden, so "secure" is not true.

SLIDE 2 - Abstract
-------------------------------------------------------------------------------------------
2.1 Current:  "This project presents a multimedia system for securely embedding and extracting
               secret text messages within digital images using Least Significant Bit (LSB)
               steganography."
    Replace:  "This project presents a multimedia system for hiding and extracting text
               messages in digital images and videos using Least Significant Bit (LSB)
               steganography. The message is hidden, not encrypted."

2.2 Current:  "The technique exploits the human visual system's inability to perceive minor
               changes in pixel intensity, allowing confidential data to be hidden without
               visible distortion to the cover image."
    Replace:  "Each colour value changes by at most 1 out of 255, so the text can be hidden
               without any difference we could see in our side-by-side figures."
    Why:      we did not test human perception; "confidential" suggests secrecy we do not give.

2.3 Current:  "The system implements an encoder that converts the message into binary and
               embeds it sequentially into image pixels with a delimiter marking the message
               boundary, and a decoder that extracts and reconstructs the original message
               from the stego-image."
    Replace:  "The encoder converts the message to UTF-8 bits and writes them, after a 13-byte
               header (signature, version, length, CRC32), into the last bits of the R, G, B
               values of the image or of each video frame. The decoder reads the header, then
               exactly 'length' bytes, checks the CRC32 and returns the exact message or a
               clear error."

2.4 Current:  "Stego-Image" / "Visually identical to the original"
    Replace:  "Stego image / video" / "No visible difference in our side-by-side figures"

2.5 Current:  "No perceptible distortion • Low computational complexity"
    Replace:  "Max change 1 per colour value • PSNR 51.1-71.4 dB measured on our covers"

C. Other measured numbers

     PSNR 51.1393 dB (theory 0.5 and 51.1411 dB).
   * Synthetic timing test (SP5): 10 s 640x480 25 fps clip with a 1,000,008-byte message:
     encode 1.13 s, decode 1.31 s; MKV 13,497,659 bytes vs 1,236,974 bytes H.264 (10.9 x).
   * Synthetic image test (SP4): 4000 x 3000 RGB, 1,020,000-byte message: encode 4.68 s,
     decode 0.71 s.
   * Automated tests: 181 passed (clean run, twice; also in a fresh clone with a new venv).

D. LIMITATIONS - measured or verified in this project
   * JPEG re-save (quality 95, and quality 100 with 4:4:4) of a stego PNG
     -> "No hidden message"; only 51-62 % of the hidden bits survived (chance = 50 %).
   * H.264 re-encode of a stego MKV (ffmpeg defaults, yuv420p, and crf 0 yuv444p)
     -> "No hidden message". Exception: libx264rgb -crf 0 (lossless RGB) kept the message.
   * Resize to 99 %, or crop 1 pixel from the left or top -> message lost. Cropping the right
     or bottom edge keeps it only if no message pixels are removed (52-byte message survived a
     1-pixel right crop of a 320-pixel-wide image; a 3,000-byte message did not).
   * When a damaged file fails, the decoder reports an error; it never returned wrong text.
   * Phone-video rotation: FFmpeg's default auto-rotation scrambles the bits (first hidden
     bytes became ff ff ff ff instead of "LSBS"); we read/write with -noautorotate and copy
     the rotation angle. A flip in the display matrix is not carried over (verified).
   * Variable-frame-rate videos and 16-bit PNGs are rejected with a clear message.
   * Output video size: 42 x (1 %) to 72.7 x (100 %) larger than the H.264 cover for our real
     clip; 10.9 x for the synthetic test clip.
   * Histograms (seen in our data; no detection test run): LSB replacement evens out value
     pairs. Macaw, red, 100 %: value 232 went 726,161 -> 557,955 pixels, value 233
     336,473 -> 504,679; the pair total 1,062,634 is unchanged. This is the effect the
     chi-square attack uses. WE DID NOT RUN A DETECTION TEST.
   * No encryption: anyone who knows the format can read the message ("LSBS" signature).
   * Text only.
